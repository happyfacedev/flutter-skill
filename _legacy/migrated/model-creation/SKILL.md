# Model Creation

Models in this project are `@freezed` immutable classes generated by the `simple_freezed_model` mason brick. Each model lives in its own file under the feature's `models/` directory, organized by role.

Cubit states are the **only** Dart classes that aren't generated this way — they use manual `copyWith` (see `cubit-creation` skill). Failure models use a different shape entirely — see `failure-modeling`.

## Critical Rules

1. **ALWAYS use the mason brick — never create models manually.** *Why:* the brick generates the boilerplate, part directives, and `fromJson` factory in one go. Hand-rolled models drift from the convention and miss the JSON serialization plumbing.
   ```bash
   mason make simple_freezed_model --name model_name --output-dir <target_directory>
   ```

2. **Keep the class `abstract`.** *Why:* Freezed requires the `abstract` modifier for its code-gen. Changing to a concrete class breaks `_$ModelName` mixin generation. Modify the factory parameters; leave the class declaration alone.

3. **Cubit states are the exception** — they're created manually (see `cubit-creation`).

4. **Run `dart tools/fix_part_directives.dart` after `mason make`** — every time. *Why:* the brick emits adjacent-path part directives (`part 'my_model.g.dart';`), but generated code in this project lives in a separate mirror under `lib/core/generated/<same-path>/`. The script rewrites the part directives into deep-relative paths to that mirror (e.g. `part '../../../../../core/generated/features/.../my_model.g.dart';`). Without the script, `build_runner` either writes to the wrong place or the file can't find its generated half. Treat the analyzer error after `mason make` and before the script as expected.

5. **Generated code is not the source file's neighbor.** *Why:* the fix script's output is what the analyzer eventually sees. The deep relative path is correct — don't "tidy" it back to an adjacent form, and don't manually edit the `core/generated/...` tree (it's regenerated on every build).

## Naming & Organization

- **Any model that maps a wire-shape → `Response` suffix, filed under `responses/`.** `UserResponse`, `NotificationPreferencesResponse` — not `User`, not `NotificationPreferences`. This applies whether the JSON comes from a REST endpoint, an RPC return value, or a Supabase `.from(...).select()` row. The suffix labels the **shape**, not the read/write direction.
- **The same model is allowed to round-trip.** A `NotificationPreferencesResponse` read via `.select().single()` may be sent back via `.upsert(model.toJson())` — do not duplicate it as a `*RequestBody` twin that always drifts. Only introduce a separate `*RequestBody` when reads and writes use **different** shapes (server returns extra computed columns, client sends a subset).
- **Bare-name domain models are reserved for a deliberate domain layer**, constructed from one or more responses (`User.fromResponse(UserResponse)`). Skip the domain layer unless explicitly required — most features in this codebase do.
- **Folder structure** under `lib/features/<feature>/logic/models/`:
  - `responses/` — every model parsed from JSON (REST responses, RPC payloads, Supabase table rows — even when the row is also used as an upsert input)
  - `request_bodies/` — request body shapes that have no read counterpart (only when reads and writes use distinct shapes)
  - `<feature>.dart` (root) — a domain model, only when a deliberate domain layer is required
  - **Do not put failure models here.** Failures go in `lib/features/<feature>/logic/failures/` and follow the `failure-modeling` skill.

## Checklist

- [ ] Created via `mason make simple_freezed_model` (not hand-written)
- [ ] Class is `abstract`; only the factory body was modified
- [ ] Package imports used (`package:your_app/...`), never relative
- [ ] `dart tools/fix_part_directives.dart` was run after creation
- [ ] Every JSON-mapped model has the `Response` suffix and lives in `responses/` — including Supabase rows used for both read and upsert
- [ ] Filed under `responses/` or `request_bodies/` — never flat in `models/` (unless a deliberate domain layer is required)
- [ ] Snake_case API fields wired with `@JsonKey(name: '...')`
- [ ] Enums (if any) mapped with `@JsonValue('...')` per variant
- [ ] Failure models (if any) are routed through the `failure-modeling` skill instead
