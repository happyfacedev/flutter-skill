# Model Creation

Models are `@freezed` immutable classes generated by the `simple_freezed_model` mason brick. Each model lives in its own file under the feature's `models/` directory, organized by role.

Cubit states are the **only** Dart classes that aren't generated this way — they use manual `copyWith` (see the cubit-creation pattern). Failure models use a different shape entirely — see the failure-modeling pattern.

## Critical Rules

1. **ALWAYS use the mason brick — never create models manually.** *Why:* the brick generates the boilerplate, part directives, and `fromJson` factory in one go. Hand-rolled models drift from the convention and miss the JSON serialization plumbing.
   ```bash
   mason make simple_freezed_model --name model_name --output-dir <target_directory>
   ```

2. **Keep the class `abstract`.** *Why:* freezed 3 requires an explicit `abstract` (or, for multi-constructor unions, `sealed`) modifier for its code-gen. Changing to a concrete class breaks `_$ModelName` mixin generation. Modify the factory parameters; leave the class declaration alone. Freezed 3 also removed `.when()`/`.map()` — consume models with Dart 3 `switch` pattern matching, never those legacy combinators.

3. **Cubit states are the exception** — created manually per the cubit-creation pattern.

4. **Run `dart tools/fix_part_directives.dart` after `mason make`** — every time. *Why:* generated code in this stack lives in a mirror tree under `lib/core/generated/<same-path>/`, NOT next to the source file. The brick emits adjacent-path part directives; the script rewrites them into deep relative paths pointing at the mirror (e.g. `part '../../../../../core/generated/features/.../my_model.g.dart';`). **That deep relative path is the correct, intended final state** — it is not a mistake to fix. Analyzer errors between `mason make` and running the script are expected. Every model has exactly two parts: `<name>.freezed.dart` and `<name>.g.dart` (the standard freezed / json_serializable extensions).

5. **Never hand-edit the part directives or the `core/generated/...` tree.** *Why:* the script's output is what the analyzer needs, and the mirror is regenerated on every `dart run build_runner build --delete-conflicting-outputs`. Don't "tidy" the deep path back to an adjacent form.

## Naming & Organization

- **Any model that maps a wire-shape → `Response` suffix, filed under `responses/`.** `UserResponse`, `NotificationPreferencesResponse` — not `User`, not `NotificationPreferences`. This applies whether the JSON comes from a REST endpoint, an RPC return value, or a Supabase `.from(...).select()` row. The suffix labels the **shape**, not the read/write direction.
- **The same model is allowed to round-trip.** A `NotificationPreferencesResponse` read via `.select().single()` may be sent back via `.upsert(model.toJson())` — do not duplicate it as a `*RequestBody` twin that always drifts. Only introduce a separate `*RequestBody` when reads and writes use **different** shapes (server returns extra computed columns, client sends a subset).
- **Bare-name domain models are reserved for a deliberate domain layer**, constructed from one or more responses (`User.fromResponse(UserResponse)`). Skip the domain layer unless explicitly required — most features don't need it.
- **Folder structure** under `lib/features/<feature>/logic/models/`:
  - `responses/` — every model parsed from JSON (REST responses, RPC payloads, Supabase table rows — even when the row is also used as an upsert input)
  - `request_bodies/` — request body shapes that have no read counterpart (only when reads and writes use distinct shapes)
  - `<feature>.dart` (root) — a domain model, only when a deliberate domain layer is required
  - **Do not put failure models here.** Failures go in `lib/features/<feature>/logic/failures/` and follow the failure-modeling pattern.

## Checklist

- [ ] Created via `mason make simple_freezed_model` (not hand-written)
- [ ] Class is `abstract`; only the factory body was modified
- [ ] Package imports used (`package:<app>/...`), never relative
- [ ] `dart tools/fix_part_directives.dart` was run after creation; deep relative part paths left as the script wrote them
- [ ] Every JSON-mapped model has the `Response` suffix and lives in `responses/` — including Supabase rows used for both read and upsert
- [ ] Filed under `responses/` or `request_bodies/` — never flat in `models/` (unless a deliberate domain layer is required)
- [ ] Snake_case API fields wired with `@JsonKey(name: '...')`
- [ ] Enums (if any) mapped with `@JsonValue('...')` per variant
- [ ] Collections use `@Default([])` (never nullable); `@Default` not relied on for fields the backend may send as explicit `null` (default only covers missing keys)
- [ ] Failure models (if any) routed through the failure-modeling pattern instead
